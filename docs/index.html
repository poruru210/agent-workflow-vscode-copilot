Agent Workflow
の動きを理解する

このページでは、Copilot版ワークフローがどの順序で進み、どこで分岐し、どこへ戻るのかを可視化します。通常時の流れ、OrchestratorによるSubagent委譲、失敗時の診断・修正を別々の図に分けています。

基本フロー = 上から下へ進む通常時の流れSubagent委譲 = 結果を元のフェーズへ戻す失敗時 = 変更内容に応じた地点から再開監査 = 対象を読み取り専用に保つ
重要：Subagent委譲と失敗時の診断・修正は、基本フローとは別に常時進む工程ではありません。必要な場面でだけ基本フローから分岐し、結果を反映して戻ります。

まず全体を単純化すると、通常時はこの流れです。

まず、この3つの動きだけ押さえる

詳細なフェーズを見る前に、「通常時」「Subagentへ委譲する時」「失敗した時」の関係を分けて理解すると、全体を追いやすくなります。

1. 通常時は、この一本道を進む

依頼を受けるCompactで済むかを最初に判定
準備する成功条件 / リスク / Baseline / 作業種別
実装・変更する設計・根本原因・介入方針に沿って変更
Snapshotを固定する以後の監査・検証対象を明確化
監査・検証する早期独立監査 → 区分ごとの検証 → 最終独立監査
完了判定する成果鍵 ＋ 独立反証鍵でGo/No-Go
2. Subagentが必要な時

現在のフェーズから、範囲を限定した作業だけを一時的にSubagentへ委譲します。完了結果は親Orchestratorが受け取り、元のフェーズの判定へ戻します。

3. FAILまたは未証明になった時

いったん診断・修正へ分岐します。根本原因と変更影響を整理したあと、何を変更したかに応じて再開地点を決めます。

復帰先の考え方：候補成果物を変えたなら新しいSnapshotを固定するところからやり直す。テスト計画だけならテスト準備の再確認へ戻る。追加証拠だけなら、その証拠が関係する命題だけを再判定する。外部操作の計画や対象が変わったなら実行準備からやり直します。
01 / Bootstrap

最初にCompact経路か通常フローかを分ける

短い読み取り専用の回答だけは軽量経路を使えます。変更、テスト、監査、Subagent委譲、重大なリスクを伴う場合は通常フローへ進みます。

すべて満たす？

  2. 必要な最新性だけを確認
  3. 回答 ＋ 限界

いいえ / 不確実 → 通常フロー

03 / Subagent委譲

現在のフェーズから作業を切り出し、結果を同じフェーズへ戻す

Subagent委譲は、基本フローとは別に進む工程ではありません。親Orchestratorが必要と判断したフェーズの中で、範囲を限定した作業だけを一時的にSubagentへ任せます。

基本フロー進行中フェーズの管理責任を持つ

04 / 失敗時の診断・修正

失敗時だけ基本フローから診断・修正へ分岐する

いずれかのフェーズがFAILまたは未証明になった場合にだけ入り、根本原因と変更影響を整理してから、変更内容に応じた地点から再開します。

06 / 動的モデル選択

モデルはSubagentを呼び出す直前に選ぶ

役割別エージェントにはモデルを固定しません。作業要件と現在利用できるモデル一覧から、要件を満たしつつ過剰でないモデルを選びます。

Job Lease（委譲条件）作業種別 / 必要コンテキスト / 利用ツール / 曖昧さ / 誤判定時の影響 / 独立性
#workflowModels現在利用可能なモデル一覧を取得
必須能力で絞り込み要件を満たさない候補を除外
必要十分な候補に絞る必要以上に高コストなモデルを常用しない
独立性 / コスト同じ見落としが重なるリスクと、リスクを含めた総コストを比較
runSubagent(model=…)開始前に作業名 / 選択モデル / 推論設定 / 選定理由を表示

07 / 役割別エージェント

Custom Agentは、役割・利用できるツール・権限境界を定義する

モデルは固定しません。監査担当のエージェントは、監査対象を読み取り専用に保ちます。

Workflow Researcher正本・ログ・外部情報を調査。読み取り中心。
Workflow Implementer準備ゲートに沿って実装・修正。
Root Cause Reviewer親の結論を先に見ずに根本原因を導出。読み取り専用。
Early Auditor固定Snapshotの構造とテスト準備を独立確認。読み取り専用。
Workflow TesterU1で定めた検証区分と判定基準を実行。
Final AuditorRelease Candidateを統合監査。読み取り専用。
Pre Action Auditor外部状態を変更する前に、対象・効果・安全性を確認。読み取り専用。
Orchestratorフェーズ管理、モデル選択、結果統合、Go/No-Go判定。
08 / Hooksによる境界保護

Hooksは基本フローを進めるものではなく、境界違反を防ぐ

フェーズ進行を守るための補助ガードです。Hookが動いたこと自体は、成果物の正しさを示す証拠にはなりません。

SessionStart継続状態があれば、作業再開に必要な情報を追加。
PreToolUse監査フェーズでの書き込みを拒否。読み取り専用と確認できないコマンドは確認を要求。
SubagentStart状態を引き継がない呼び出しであることを明示。
SubagentStopジョブの実行状態を完了へ更新。
PreCompactコンテキスト圧縮前にチェックポイントを保存。
Stop未解決の必須命題が残る場合、完了と誤認しないよう警告。
09 / 証拠の整理

別々の確認事項を「テストが通った」だけで一括判定しない

根本原因、検出漏れ、介入方針、変更安全性、停止条件の組み合わせ、検証モデルを別々の証拠記録として保持し、最終的に成果鍵と独立反証鍵を閉じます。
