Agent Workflow
の動きを理解する

「Copilot版ワークフローがどう動くか」だけを可視化します。 通常時の流れ、OrchestratorによるSubagent委譲、失敗時の診断・修正を別々の図に分け、相互関係が必要な箇所だけを示します。

基本フロー = 上から下へ進む通常時の流れ Subagent委譲 = 現在のフェーズから呼び出し、結果を同じフェーズへ戻す 失敗時 = 診断・修正へ分岐し、変更内容に応じた地点から再開する 監査 = 対象を読み取り専用に保つ
重要： Subagent委譲と失敗時の診断・修正は、基本フローと並行して常時進む別工程ではありません。必要な場面でだけ基本フローから分岐し、結果を反映して戻ります。

まず、この3つの動きだけ押さえる

詳細なフェーズを見る前に、「通常時」「Subagentを使う時」「失敗した時」の関係を分けて理解すると、全体が追いやすくなります。

1. 通常時は、この一本道を進む

2. Subagentが必要な時

現在のフェーズから、範囲を限定した作業だけを一時的にSubagentへ委譲します。完了結果は親Orchestratorが受け取り、元のフェーズの判定へ戻します。

3. FAILまたは未証明になった時

いったん診断・修正へ分岐します。根本原因と変更影響を整理したあと、何を変更したかに応じて再開地点を決めます。

復帰先の考え方： 候補成果物を変えたならSnapshotからやり直す。テスト計画だけなら検証準備へ戻る。追加証拠だけなら、その証拠が関係する命題だけを再判定する。外部操作の計画や対象が変わったなら実行準備からやり直します。

03 / Subagent委譲

基本フローの現在位置からSubagentへ分岐し、結果を同じフェーズへ戻す

Subagent委譲は別工程として並行するのではなく、基本フローの現在フェーズから範囲を限定した作業だけを一時的に切り出す動きです。

青が現在のフェーズです。この位置から作業パッケージだけをSubagentへ委譲し、結果は同じ位置へ戻します。
なぜ分岐する？

現在のフェーズの一部を、独立したコンテキスト・役割・権限境界で確認する価値があるためです。

何をする？

Job Leaseを固定し、現在利用可能なモデルから必要十分なものを選び、範囲を限定してSubagentへ委譲します。

どこへ戻る？

Subagentの完了結果を親Orchestratorが統合し、委譲元と同じフェーズの判定へ戻します。

→
Early Independent Audit から委譲独立した確認が必要な範囲だけをJob Leaseとして切り出す
1. Job Lease目的 / 対象範囲 / 権限 / 必要証拠 / 独立性を固定
2. #workflowModels現在利用できるモデル一覧を取得
3. モデルを選択作業要件を満たし、過剰でないモデルを選ぶ
4. runSubagent()役割別エージェントを、状態を引き継がない呼び出しとして実行
Subagentの完了結果を親Orchestratorが統合指摘 / 証拠 / 未証明事項を正本と照合し、Early Independent Audit の「PASS / 修正要 / 未証明」判定へ戻す
見方： 青い矢印が委譲、緑の破線が結果の返却です。フェーズ全体の管理責任は親Orchestratorに残り、Subagentの処理が終わると基本フローの同じフェーズへ戻ります。
04 / 失敗時の診断・修正

基本フローの失敗地点から診断・修正へ分岐し、変更内容に応じた地点から再開する

失敗時だけ基本フローから一時的に分岐します。根本原因と変更影響を整理したあと、何を変更したかに応じて再開地点を選びます。

なぜ分岐する？

FAILの根本原因を確定する前に、その場しのぎの修正へ進まないためです。

何をする？

証拠を保存し、RC / VER / TEST-RCを分離して根本原因を確認し、原因となる経路へ介入します。

どこへ戻る？

候補成果物、テスト計画、追加証拠、外部操作のどれを変更したかに応じて、基本フロー上の再開地点を選びます。

!
Partitioned Verification でFAILその場しのぎで修正せず、まず証拠と失敗分布を保存する
1. 証拠を保存入力 / 状態 / ログ / 対象の識別情報 / 実行環境
2. RC / VER / TEST-RC最初の異常地点 / 責任層 / 検出漏れ / 検証側の根本原因を分離
3. 根本原因を独立確認必要なら親の結論を先に見せず、読み取り専用で独立に原因を導出
4. 介入方針 / 修正症状ではなく、原因となる経路や共有する仕組みを修正
5. 新しいSnapshot / 変更影響 / U1実際の変更差分と影響範囲を改めて導出
復帰先を判定常に同じ場所へ戻るのではなく、何を変更したかに応じて基本フローの再開地点を決める
候補成果物を変更→ Implementation Snapshot から再開
テスト計画だけ変更→ テスト準備の再確認 → 必要な検証
追加証拠だけ→ 該当する命題だけ限定再判定
外部操作の計画・対象・権限を変更→ 実行準備ゲートから再開
この例の復帰： 修正によって候補成果物を変更したため、緑の破線は Implementation Snapshot に戻ります。テスト計画だけの変更や追加証拠だけの場合は、右側の復帰判定に示した別の地点から再開します。

07 / 役割別エージェント

Custom Agentは、役割・利用できるツール・権限境界を定義する

モデルは固定しません。監査担当のエージェントは、監査対象を読み取り専用に保ちます。

Workflow Researcher正本・ログ・外部情報を調査。読み取り中心。
Workflow Implementer準備ゲートに沿って実装・修正。
Root Cause Reviewer親の結論を先に見せない根因導出。READ ONLY。
Early Auditor固定Snapshotの構造とテスト準備を独立確認。読み取り専用。
Workflow TesterU1で定めた検証区分と判定基準を実行。
Final AuditorRelease Candidateを統合監査。読み取り専用。
Pre Action Auditor外部状態を変更する前に、対象・効果・安全性を確認。読み取り専用。
Orchestratorフェーズ管理、モデル選択、結果統合、Go/No-Go判定。
08 / Hooksによる境界保護

Hooksは基本フローを進めるものではなく、境界違反を防ぐ

フェーズ進行を守るための補助ガードです。Hookが動いたこと自体は、成果物の正しさを示す証拠にはなりません。

SessionStart継続状態があれば、作業再開に必要な情報を追加。
PreToolUse監査フェーズでの書き込みを拒否。読み取り専用と確認できないコマンドは確認を要求。
SubagentStart状態を引き継がない呼び出しであることを明示。
SubagentStopジョブの実行状態を完了へ更新。
PreCompactcontext圧縮前にチェックポイントを保存。
Stop未解決の必須命題が残る場合、完了と誤認しないよう警告。
09 / 証拠の整理

別々の確認事項を「テストが通った」だけで一括判定しない
