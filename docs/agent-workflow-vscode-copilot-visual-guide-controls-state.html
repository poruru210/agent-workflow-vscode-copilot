04 / 失敗時の診断・修正

FAIL地点から診断へ分岐し、変更内容に応じて再開する

その場しのぎの修正へ進まず、まず根本原因を確認します。

停止中
通常FAIL再開候補
基本フロー
なぜ分岐する？

根本原因を確定する前に局所修正へ進まないため。

何をする？

証拠保存 → RC / VER / TEST-RC → 根本原因確認 → 修正。

どこへ戻る？

何を変更したかに応じ、Snapshot・検証準備・限定再判定などへ戻る。

証拠を保存入力 / 状態 / ログ / identity / 環境
RC / VER / TEST-RC最初の異常地点・検出漏れ・検証系根因を分離
根本原因を独立確認必要なら親の結論を先に見せず確認
INT / 修正症状ではなく原因となる経路へ介入
再開地点を判定候補成果物変更→Snapshot / テスト計画→検証準備 / 追加証拠→限定再判定
未証明だけの場合： 必要証拠が不足しているだけなら、直ちに修正へ進まず、追加証拠取得・限定再判定・正確な阻害記録を優先します。

07 / 証拠の整理

別々の確認事項を「テストが通った」だけで一括判定しない

RC根本原因
VER / TEST-RC / VM検出漏れ・検証系根因
INT / CHG / CONT介入・変更安全・停止合成
U0 → U1 / Evidence Map検証母集団と証拠依存
成果鍵 + 独立反証鍵が閉じて初めて Completion / Go
詳細な規範・例外条件はrepository内のpolicyを正本とします。
